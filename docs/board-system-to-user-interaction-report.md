## Scope

This diagram covers only board-page product interactions where the system initiates visible feedback toward the user. It intentionally avoids route/store/database architecture detail except where needed to explain why a UI signal appears.

## Design Choices

- The SVG uses three columns: `SYSTEM EVENT`, `VISIBLE UI SIGNAL`, and `USER RESPONSE`. This keeps the diagram centered on product behavior rather than implementation architecture.
- The rows group related system-initiated interactions: access revoked, realtime board changes, presence, activity feed refresh, errors and retry, undo banner, notifications/watchers, and empty/filtered states.
- Color is used by interaction type: warning for access loss, blue/purple for live system updates, red for recoverable failures, green for user response, and neutral for empty states.
- I included only implementation labels that explain the user-visible behavior, such as `router.refresh`, `errorBus`, and `undoBus`; low-level database and component hierarchy details are deliberately omitted.

## Evaluation

The result matches the clarified request: it is a product interaction flow diagram, not a code architecture diagram. It explains what the system detects, what the user sees, and what action or understanding the UI enables. The strongest coverage is realtime updates, errors, undo, and access notices because those flows have direct code evidence. Notifications are included because the board creates and consumes watch/assignment/mention-style signals through the global bell, even though the bell is mounted in navigation rather than inside the board body.
