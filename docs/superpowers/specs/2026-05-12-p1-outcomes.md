## The three things we investigated

### 1. "How do roles work and so on" (your task #1)

You wanted a clear explanation of who can do what in the app.

**What we found**: There are three separate kinds of permissions in the app, working at three different levels.

- **Workspace level** — Owner, Admin, Member. Controls big things like creating boards and inviting people.
- **Board level** — Admin, Member, Observer. Controls who can edit a board's cards and lists.
- **Dashboard level** — Owner, Editor, Viewer. Controls who can edit shared dashboards.

A person can have a different role on each level. Being an admin of the workspace doesn't automatically make you an admin of every single board, and vice versa.

**What we wrote**: A full reference document at [`docs/roles.md`](../../roles.md) with tables showing exactly what each role can and can't do. New team members can read it to understand the system.

**Bonus finding**: While reading the permission rules, we noticed four small security weaknesses in the app:

1. A workspace admin could secretly promote someone to owner using a direct call (the UI hides this option but the code doesn't block it).
2. There's an inconsistency in how SLA rules can be edited — a board admin can delete one but not create one. Probably a typo in the original setup.
3. A board admin can promote anyone else to board admin without any limit.
4. The system has an "owner" role but no billing or payment system to gate (so the owner role doesn't really do anything extra beyond deleting the workspace).

These weren't on your list. We wrote them down. We are NOT fixing them in this round. They can be a separate clean-up later.

### 2. "Clicking a card opens a new URL instead of opening details in the same page" (your task #2)

You said: when I click a card, it goes to a new page instead of opening a quick details popup. This is annoying and makes the app feel slow.

**What we found**: The app is set up correctly to show a popup. The code for the popup exists. The wiring is right. But something is causing the browser to do a "full page reload" instead of using the popup. The most likely cause is that the click is sometimes being interpreted as a real navigation (like typing a URL in the address bar) instead of a quick popup-open.

Think of it like a door that's supposed to swing open inside your house, but the hinge sometimes catches and the whole door falls outside instead.

**What we'll fix**: Change how the click is handled so it's always treated as "open the popup", never as "go to a new page". Small, surgical change.

There's a 5-second test we want to do first to be 100% sure of the cause: open the browser's developer tools and click a card while watching the network. If we see a full HTML page download, the fix is the right one. If we see only data fragments downloaded, there's something deeper going on. We'll do that test before the fix to avoid wasting time.

### 3. "Browser gets stuck after a while" (your task #4)

You said: after using the app for a while, the browser slows down and freezes, even though there isn't much data. You blamed the activity log ("talk") having no limit.

**What we found**: The activity log IS limited (50 entries for the board, 30 for a card). So your guess about the cause wasn't quite right. But the freezing IS real, and we found three actual causes that all stack up over time.

**Cause 1 — Constant page refreshes**

Every time anyone makes any change in the app (a comment, a label, moving a card), the app re-downloads the entire board page. It only needs to update that one small thing, but it refreshes everything. After hundreds of small changes during a busy day, that's hundreds of full re-downloads. The browser starts to choke.

*Fix*: Instead of re-downloading the whole page each time, update only the bit that changed. Or, at minimum, group bursts of changes together so we refresh once per second instead of fifty times.

**Cause 2 — Comments piling up in memory forever**

The app keeps every comment from the whole board loaded in the browser's memory, even comments you can't see. It never throws old ones away. And the comments section is set up so that whenever ANY comment arrives, every open comment panel on the page re-draws itself. With 500 comments accumulated, opening a new card has to dig through all 500.

*Fix*: Make the comments panel look at only the comments for the card you're viewing, not all comments everywhere. Also, cap the total at a sensible number (maybe 200 per card) so memory doesn't grow forever.

**Cause 3 — Live updates resetting themselves**

The app keeps a live connection open to the database so it can show updates in real time. But the way the code is written, every time the board list changes shape (e.g. you renamed a board), the live connection tears down and rebuilds itself. Doing this constantly wastes resources.

*Fix*: Make the live connection care only about which workspace you're in, not about every detail of the board list. Then it stays steady.

**Smaller things we found**

There are two more small inefficiencies (an error log that grows forever, and a slightly fragile reference in the same file as Cause 1). They're not urgent. We'll skip them in this round.

## Glossary (in case any term wasn't clear)

- **Codex agent**: an AI helper we send a specific task to. It works on its own and reports back.
- **Worktree**: an isolated copy of the codebase, so an agent can experiment without affecting the main code.
- **RSC / refresh**: when the app asks the server "send me this page again from scratch".
- **Selector**: the code that picks which slice of memory a UI component watches.
- **Realtime channel**: a live connection to the database that pushes updates as they happen.
- **Intercept route / popup route**: a Next.js feature where clicking a link opens a popup instead of going to a new page.
- **RLS (row-level security)**: rules in the database that decide who can read or write each row.
